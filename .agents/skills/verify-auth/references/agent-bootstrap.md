Each `harness-<receipt>.json` carries `ready` and `readinessEvent` (`proof-bundle-artifacts.ts` `authHarnessReadinessSchema`). The runner refuses any receipt that isn't `ready: true`, and any event the journey doesn't accept: `bootstrap` and `agent` accept `jwks` or `personToken`; `people` also accepts `signInSession`. Readiness only ever strengthens (`personToken` > `jwks` > `signInSession`), so a later callback never replaces an earlier, stronger witness. Each receipt also carries `requestLimits` (`authHarnessRequestLimitsSchema`): its outer counter and the request-limit observations the host drained. Node receipts must say `node-fixed-window`. Cloudflare receipts require `cloudflare-real-binding`, except for exactly one `cloudflare-controlled-binding-stand-in` in `people` on workerd with the schema-bound `proofCase: service-page-exact-budget` and no backing failure. This case keeps native HTTP, adapter and address keying but controls the counter's window, because Miniflare's real windows follow the wall clock. It requires first 429 at request 301, unchanged state and a second address passing; it earns no real-limiter or vendor credit. The separate workerd real-binding wiring case requires an actual 429 by request 601 (at most one rollover), unchanged state and another address passing. Neither test reads or waits on real time. Missing, duplicate, unnamed, unrelated or wrong-journey stand-ins refuse the run, as does a stand-in on Node or any other counter. `requestLimits.backingFailure` must be `none` everywhere, except exactly one `people` receipt per host: `node-counter-throws` on Node, `cloudflare-binding-rejects` on Cloudflare. The compared target and the printed summary report the counter mix, the 429s by layer (`outer`, `provider`), the unavailable count, the backing-failure kinds and `cloudflareVendorCredit: false`.
